# Design review — 26 confirmed findings

> Adversarial review of the architecture plan. Severity-ordered. Mitigations applied to the scaffold are noted in PLAN.md / code.

### [CRITICAL] The optimizer/Brier loop — pitched as the rewrite's 'strategic payoff' — has ZERO training data and no near-term path to any
**Area:** DSPy optimizer / eval loop realism

**Problem:** The plan repeatedly frames DSPy's MIPROv2/Brier-metric compilation against forecast_resolutions as the central justification for going Python+DSPy ('the strategic payoff', 'the major DSPy payoff', 'closes the eval/optimization loop'). I queried the live data/dana.db (32MB, the file the plan treats as the proof of a real corpus): forecast_resolutions = 0 rows, topics = 1, final_verdicts = 1, expert_assessments = 0, and the single topic is stuck at status review_enrichment — it has never completed a pipeline, let alone been resolved. There is not one labeled example. A geopolitical forecast resolves on the order of months-to-years after it is made; even under heavy use, getting to the plan's own stated MIPROv2 threshold (~200 examples, or even the BootstrapFewShot floor of ~15-30) is a multi-year data-collection problem, not an engineering one. DSPy optimizers cannot manufacture signal from nothing — with n=0 the entire optimize/ subsystem, the CI eval gate, the 'compiled scorer improves held-out Brier' Phase-3 acceptance criterion, and the adversarial-steering regression probe are all undeliverable as specified.

**Recommendation:** Demote the optimizer loop from headline justification to a clearly-labeled future bet, and DO NOT let it drive any architectural decision that costs effort now. Concretely: (1) Re-justify the rewrite on grounds that actually hold day-one — typed Signatures killing the 52 regex/JSON.parse sites, ReAct replacing the agentic loop, STORM research depth — none of which need resolutions. (2) Replace the Brier-compile acceptance criteria in Phases 3-4 with criteria that are satisfiable now: e.g. MIPROv2 optimizing the scorer against a *proxy* metric on synthetic/back-tested scenarios, or simply 'eval harness runs and reports insufficient-data' (which the plan already concedes as the cold-start path — make that the *primary* path, not the fallback). (3) Build optimize/ last and smallest; ship the platform without it. (4) If forecast accuracy is genuinely the goal, the higher-leverage near-term move is instrumenting resolution capture and seeding back-tested historical scenarios, not building a MIPROv2 harness that will sit idle.

### [CRITICAL] Cross-process write hazards are under-mitigated: customProviders whole-list PUT, states.id AUTOINCREMENT, and an advisory lock the TS backend doesn't honor
**Area:** Side-by-side cutover / data integrity

**Problem:** Three concrete two-writer hazards the plan waves away with 'WAL + one writer + a pipeline_owner advisory lock': (1) customProviders.ts serializes mutations with a PROCESS-LOCAL mutex because each change is a read-modify-write against the proxy's WHOLE-LIST management PUT. With two backends, a Python `asyncio.Lock` and a TS in-process mutex cannot see each other — concurrent custom-provider edits from both backends clobber the entire provider list at the proxy, not just risk a DB row. This is shared MUTABLE PROXY STATE, not SQLite, so WAL doesn't help at all. (2) `states.id INTEGER PRIMARY KEY AUTOINCREMENT` and `research_searches`/`research_pages` autoincrement ids: two processes inserting concurrently rely on SQLite's per-writer locking, which is safe for the id itself, but the plan's proposed `pipeline_owner:<topic_id>` advisory lock is a NEW Python-side convention the RUNNING TS backend has no knowledge of — the TS `activeRuns` is a per-process Map and will happily start a run on a topic Python 'owns'. The advisory lock only works if BOTH backends check it, which would require modifying the supposedly-frozen TS backend. (3) The plan never addresses that `current_version` on topics and the `states` version counter can be advanced by either backend, so a fork/version allocation racing across processes can collide on `(topic_id, version)` despite the unique index (one insert just fails).

**Recommendation:** State an explicit, enforceable cutover rule: a given topic is owned by exactly ONE backend, enforced operationally (route the topic's traffic), not by an advisory lock the TS side ignores. For provider/settings management (global, not per-topic), pick ONE backend as the sole writer of provider/custom-provider/settings during the window — do not let both write proxy management state. If the TS backend must remain a writer, add the `pipeline_owner` check to it too (contradicting 'frozen TS'), or accept that providers management is Python-only or TS-only, not both. Add a test that two concurrent custom-provider PUTs (one per backend) don't lose providers.

### [HIGH] The per-model rate limiter is bypassed by DSPy/litellm unless every LM call is forced through one chokepoint, while the design's three independent fan-out sources defeat the bucket anyway
**Area:** rate limiting / concurrency

**Problem:** The TS TokenBucket (proxyClient.ts:53-99) works because EVERY call goes through chatCompletion(), which awaits limiter.acquire() before fetch. The plan routes structured calls through dspy.LM (litellm) and STORM grounded conversation through raw litellm acompletion. DSPy/litellm has no hook to await an external aiolimiter before each provider request; litellm's own RPM limiter is a different mechanism. The plan's claim (Foundations 6, Infra 5) that the bucket lives 'inside the LM wrapper' only holds if you subclass dspy.LM and override the request method, and even then DSPy optimizers, dspy.Parallel(num_threads=8), and module.batch() spawn calls through paths that may not hit your override (compiled programs, JSONAdapter reparse re-calls). Meanwhile the design explicitly fans out STORM conversations with asyncio.gather + Semaphore, AND ensemble scorer runs with gather, AND per-party enrichment with gather, three independent concurrency sources all hitting opus/sonnet simultaneously. opus burst=5/rps=2 is exhausted instantly by e.g. 6 parallel party conversations each doing a tool round, producing 429 storms that fall to litellm's blind backoff with no shared token accounting.

**Recommendation:** Make the limiter a single global asyncio singleton (one aiolimiter per model id) and force ALL LM traffic through one async function that resolves the available model, awaits acquire(), then calls litellm. Wire dspy.LM to it by overriding aforward/forward; do not rely on litellm's internal limiter. Cap total concurrency at the SOURCE with a single global Semaphore sized to the tightest tier, shared across STORM conversations, ensemble runs, and enrichment batches, not three independent semaphores. Add a test that spawns N>burst concurrent calls and asserts zero 429s reach the provider. Verify dspy.Parallel/batch honor the override before using them; otherwise replace with your own gather over acall.

### [HIGH] emit() with put_nowait + drop-on-full silently loses lifecycle events (forum_turn, clue_discovered, stage_complete, verdict_content) under the load the redesign creates
**Area:** SSE delivery

**Problem:** The TS bus calls subscriber callbacks synchronously and the ReadableStream enqueues immediately, so events are effectively never dropped for a connected client. The plan replaces this with a bounded asyncio.Queue(maxsize=1000) and put_nowait that DROPS on QueueFull (bus.py: 'except asyncio.QueueFull: pass'). STORM multi-persona conversations emit think events at very high frequency (every web_search, fetch_url, LM round, tree insert, gap-critic redirect). With several conversations concurrent plus a slow browser EventSource, the queue fills in bursts and silently drops precisely the forum_turn/clue_discovered/weight_result/stage_complete events the frontend needs for correctness, not just cosmetic think spam. A dropped stage_complete or verdict_content means the UI never advances, indistinguishable from a hang. Two browser tabs on one topic independently drop different events and diverge.

**Recommendation:** Separate events by criticality. Lifecycle/terminal events (progress, stage_complete, verdict_content, weight_result, error, forum_turn, clue_discovered) must NEVER drop: use an unbounded queue or a short await-put with timeout for them, and only make the think feed lossy (coalesce progress to latest). Also note the frontend uses unnamed data: lines with no event id, so an EventSource reconnect (auto every 3s) REPLAYS NOTHING; combined with drop-on-full, any event during a reconnect window is lost forever. Add a small server-side ring buffer of the last N critical events per topic and replay on (re)subscribe, or have the frontend re-fetch authoritative state (GET /forum, /verdict) on reconnect rather than trusting the stream alone.

### [HIGH] Fire-and-forget create_task plus in-memory registry leaves runs orphaned on restart, and the advisory lock becomes a permanent stale block; resumability is weaker than claimed
**Area:** failure & resumability

**Problem:** The plan uses fire-and-forget create_task with an in-memory RunRegistry. Checkpoints (checkpointManager.ts) are STAGE-level, and the forum completed_turn_ids list is never read on restart (ForumOrchestrator always starts the debate fresh; the plan itself lists this as a future 'improvement'). If uvicorn restarts mid-Enrichment (a multi-minute, many-call stage), the in-memory registry entry vanishes, the task is dead, no partial checkpoint exists, the topic is stuck in a 'running' status with no active task and nothing re-spawns it. The cross-process pipeline_owner advisory lock makes it worse: a crash leaves a stale pipeline_owner:<topic_id> row that permanently returns false 'already running' until manually cleared. Single uvicorn worker is assumed but never enforced; with --workers 2 the in-memory RunRegistry and TopicBus are per-process, so an SSE client may connect to a different worker than the task emitting events and receive nothing.

**Recommendation:** (1) On startup, reconcile topics in a running status with no live registry entry: auto-resume from the last checkpoint or move them to an error/needs-attention status so they aren't silently stuck. (2) Make the lock self-healing: store owning pid + heartbeat timestamp and treat a stale heartbeat as reclaimable, not a bare topic_id that blocks forever. (3) Pin and assert single-worker, OR commit to Redis pub/sub + Redis lock now if multi-worker is plausible; the in-memory bus + registry are fundamentally incompatible with >1 worker and the SSE-task-affinity problem makes 'swap later' a correctness bug, not a scaling optimization. (4) Actually implement forum turn-level resume since forum is the longest stage and the column already exists.

### [HIGH] STORM multi-persona conversations are a multiplicative token/latency explosion versus the flat per-party loop they replace; the corpus cache does not address the dominant cost (LM calls)
**Area:** token cost & latency

**Problem:** TS Enrichment does ONE agentic loop per party (PartyEnrichmentAgent: a single runAgenticLoop). The STORM redesign replaces this with, PER PERSONA (parties AND lenses, so MORE personas than parties): an analyst<->researcher conversation of max_turns rounds where each turn does QuestionToQueries (LM) + retrievals + GroundedAnswer (LM) + InsertInformation tree LM call + periodic GapCritic LM calls, then a DistillClue LM call + an adversarial FactCheck (its own ReAct loop with searches) PER emitted clue, all conversations concurrent. That is roughly (turns x ~3 LM calls) + (clues x (distill + factcheck rounds)) per persona, times (#parties + #lenses). Cost/latency is easily 5-15x the TS baseline, dominated by the strong-model calls (GroundedAnswer, DistillClue, GapCritic, FactCheck). The corpus cache mitigates duplicate FETCHES but not LM-call count, which is the real cost. Global search ceilings cause a silent quality bias: late-researched personas hit the ceiling and get INSUFFICIENT_EVIDENCE for everything, so coverage depends on research order.

**Recommendation:** Budget in LM-CALLS and tokens, not just searches, accounting strong-model calls separately. Allocate budget per-persona up front (fair-share) so late personas aren't starved. Run a cost spike test on a realistic 6-party topic end-to-end with track_usage on, comparing tokens/wall-clock/$ to the TS baseline before committing to lens-personas; if it's ~10x, gate lenses behind a control flag and default conversations to max_turns 2-3. Fact-check the top-K highest-relevance clues, not every distilled clue from every persona (the single largest avoidable cost). Cache GroundedAnswer/DistillClue by (question, retrieved-source-set) hash so near-identical persona questions don't both pay the strong-model call.

### [HIGH] STORM reference code is pinned to dspy 2.4.9 — two major lines behind the target — so 'port the patterns' hides a full rewrite against a changed API
**Area:** DSPy maturity / version risk

**Problem:** The plan's STORM-first thesis leans on porting concrete modules from /home/nima/storm (persona_generator, knowledge_curation/ConvSimulator, information_insertion_module, co_storm moderator). I checked: STORM pins dspy_ai==2.4.9 in requirements.txt. The plan targets dspy>=3.0,<3.4 (and even internally contradicts itself — different sub-sections cite 2.5, 3.2.1, and 3.3+). Between 2.4.9 and 3.x DSPy had breaking changes the plan itself lists (Assert/Suggest removed in 2.6 → Refine/BestOfN; BaseLM/dspy.LM reworked; settings/configure semantics changed; ReActV2 in 3.3+; compiled-artifact format churn; the whole LM/adapter layer rewritten). So the STORM modules cited as the porting source will not run on the target version and are not a copy-port — they are a structural rewrite against an API the reference predates. The plan's repeated 'port verbatim' / 'almost verbatim' language (esp. for the knowledge tree InsertInformationModule and the co-STORM moderator) materially understates this. Additionally, dspy is not installed anywhere in this environment, so none of the proposed API surface (signatures, ReAct, streamify, MIPROv2) has been validated against a real interpreter.

**Recommendation:** Before committing to the architecture, do a time-boxed spike: pip install the exact pinned dspy 3.x, and actually stand up ONE end-to-end slice — a typed Signature with a nested Pydantic list output through dspy.LM→CLIProxyAPI, plus a dspy.ReAct over real web_search/fetch_url, plus one streamify SSE path. Treat the STORM modules as design references, not source to port, and budget real time to rewrite the knowledge-tree and moderator logic against 3.x. Pin dspy to a single exact version (not a range) and commit uv.lock; reconcile the three conflicting version claims in the doc to one. Verify that the JSONAdapter native-structured-output path actually works through CLIProxyAPI's proxied models (many proxied/OAuth models don't honor response_format or tool-calling cleanly) — if not, the whole 'typed OutputField parses, no regex' premise degrades to ChatAdapter text-parsing, which is closer to what the TS already does by hand.

### [HIGH] dspy.ReAct(max_iters=N) does not replicate the custom agentic loop's budget protocol, per-round caps, two-phase research→store, and context compaction
**Area:** DSPy fit for long agentic loops

**Problem:** The plan maps runAgenticLoop → dspy.ReAct(tools=[...], max_iters=N) as a near-equivalence ('replaces runAgenticLoop verbatim'). Reading agenticLoop.ts (lines 137-268), the loop is far richer than ReAct's iteration cap, and 15 of ~20 agents depend on it: (a) budget-mode separating 'free' tools (store_clue) from metered research tools, counting only research rounds against the budget; (b) per-round tool caps (perRoundCaps) that reject excess parallel tool calls with a 'try next round' message; (c) a scripted two-phase protocol — at budget exhaustion it injects a 'RESEARCH PHASE COMPLETE, now batch-call store_clue for ALL findings, synthesize multi-source clues' user message, fundamentally changing agent behavior mid-loop; (d) a one-round-remaining warning nudge; (e) context-pressure detection (estimateTokens > threshold) injecting a 'wrap up' message; (f) corpus-cache short-circuit inside the tool body; (g) a hardCap = maxIter + 10 safety. dspy.ReAct gives you a tool loop and a max_iters trip-wire and a final-answer extraction — it does NOT give you metered-vs-free tool budgets, per-round caps, mid-trajectory protocol switching, or token-pressure compaction. Rebuilding these inside ReAct means subclassing/forking ReAct's forward (fighting the framework) or wrapping each tool with budget state (leaky), both of which erase the 'DSPy removes the hand-rolled loop' benefit for exactly the agents where the loop logic is load-bearing.

**Recommendation:** Do not assume ReAct is a drop-in for the research agents. Pick deliberately per agent: (1) For the structured single-shot calls (scorer, weight, persona, fact-check verdict) DSPy Signatures are a genuine win — use them. (2) For the budget-metered research loops (enrichment, discovery research, party intelligence), seriously consider KEEPING the hand-rolled loop — the Infra section already concedes this ('use litellm acompletion directly... so the existing toolDefinitions + corpus-caching/budget logic ports directly'). That concession contradicts the Foundations/Pipeline sections that map everything to ReAct; resolve the contradiction in favor of keeping the custom loop where budget logic lives, and wrap its *output* in a typed Pydantic model rather than forcing the whole loop into ReAct. (3) If ReAct is used, prototype the budget protocol inside it first and measure how much custom code survives before committing the whole research engine to it.

### [HIGH] User-editable .md prompts and DSPy optimization fundamentally conflict; 'write the optimized instruction back to the .md' will silently clobber operator edits
**Area:** Editable prompts vs. Signatures/optimizers tension

**Problem:** The plan's reconciliation — .md body becomes Signature.with_instructions(), and an optimizer writes its improved instruction back to the same .md (with backup/reset) so 'human editing and machine optimization share one artifact' — looks clean but has two real failures. First, the score-scenarios.md prompt I read is 117 lines of densely hand-tuned, interdependent reasoning rules (Step 1-7 tallying, verdict-specific weighting, cui-bono discounting, independence checks). DSPy optimizers (MIPROv2/GEPA) REWRITE the instruction wholesale — they propose new instruction candidates and keep the highest-scoring. Pointing one at this prompt means it will rewrite or discard that carefully-engineered domain logic in favor of whatever scores marginally better on a tiny eval set — and there is no eval set (Finding 1), so the 'improvement' is noise. Second, the round-trip is lossy and racy: an operator edits the .md for a live topic; an offline CI compile job later overwrites it with an optimizer candidate; the operator's intent is gone (the 'backup' is one-deep and reset goes to the builtin default, not the operator's last edit). The two writers to one artifact have no merge model. Third, DSPy adapters also rewrite the *I/O schema* portion of the prompt (field markers, formatting instructions) — operators editing the .md can easily break the parse contract the Signature depends on, with no validation that their edit still produces parseable output.

**Recommendation:** Separate the layers explicitly instead of collapsing them into one .md: keep the operator-editable .md as the human instruction layer, and store optimizer-produced artifacts as separate, versioned compiled programs (the plan already has dspy_compiled_programs / data/dspy/<hash>.json — use that as the SOLE home for machine output, never write back to .md). At runtime, decide a precedence (e.g. operator edit overrides compiled, or expose both and let the operator opt-in to a compiled candidate via the prompts UI) rather than silently merging. Never let a CI job mutate a file an operator hand-edits. Also add a validation step on prompt PUT that round-trips a sample through the Signature so an operator edit that breaks parsing is caught at save time, not at pipeline runtime. Given Finding 1, deprioritize the write-back machinery entirely for now.

### [HIGH] run_id is the literal stage name, not a UUID or run-vN — plan is internally inconsistent and breaks the contract
**Area:** REST contract / pipeline

**Problem:** The plan describes run_id three incompatible ways: `{run_id, started_at, status:"started"}` generically, `run_id = f"run-v{v}"` in the stage-executor sketch, and `"run_id": "enrich"` in the route sketch. The actual TS contract (routes/pipeline.ts: `trackRun(topicId, "discover")`, `"enrich"`, `"analyze"`, `"forum-prep"`, etc.) sets run_id to the LITERAL stage string, and that exact value is also the checkpoint directory name (checkpointManager.ts: `run-${runId}` → `data/topics/<id>/logs/run-discover/checkpoint.json`). The frontend stores and echoes run_id (client.ts types `{run_id: string}`). If Python emits `run-v3` or a UUID, (a) the frontend's returned value diverges and (b) checkpoint paths no longer match the TS backend's, breaking resumability continuity across the side-by-side window. The plan's own `run_id` is conflated with the version-snapshot's `version`, which are different concepts in the TS code.

**Recommendation:** Pin run_id to the exact stage-name strings used in pipeline.ts (`discover|enrich|analyze|forum-prep|forum|score|reanalyze|run`). Keep the checkpoint directory naming `run-<run_id>` byte-identical so a topic's checkpoints written by TS are readable by Python and vice-versa. Add a contract test asserting the run_id string for each endpoint equals the TS value. Decouple run_id (stage label) from version (state-manager integer) explicitly in the code and docs.

### [HIGH] dana-py compose service never sets MANAGEMENT_SECRET — all provider/custom-provider management routes will 401
**Area:** Provider/management parity

**Problem:** proxyAdmin.ts reads the management key from `process.env.MANAGEMENT_SECRET` only, and entrypoint.sh GENERATES/READS it from `${DATA_DIR}/.management-secret` (head -c 24 /dev/urandom on first boot, persisted with umask 077) and exports it, then injects it into the proxy config. The plan's Phase-8 compose snippet for `dana-py` sets PROXY_BASE_URL/SEARXNG_URL/etc. but NOT MANAGEMENT_SECRET, and asserts (incorrectly) that Python's proxy_admin hits `/v0/management/*` 'with the same Bearer secret from data/.management-secret'. Nothing in the plan's dana-py service actually reads that file. Result: every /api/providers (login, disconnect, models, management-status) and /api/providers/custom mutation returns 503 'management_unavailable' or 401, silently failing provider parity. This is a same-instance shared-proxy assumption that the env wiring does not satisfy.

**Recommendation:** Give dana-py its own entrypoint (or env wiring) that reads `${DATA_DIR}/.management-secret` into MANAGEMENT_SECRET before launching uvicorn — mirroring entrypoint.sh exactly, including the same file path and the no-overwrite-if-already-set behavior. Add a Phase-0 acceptance check: `GET /api/providers/management-status` returns available=true against the live proxy. Order container startup so the TS entrypoint (which creates the secret) runs first, or factor secret generation into a shared init step both containers depend on.

### [HIGH] 'JSON-as-TEXT byte-compatible' and integer-boolean round-tripping are more fragile than a single TypeDecorator implies
**Area:** DB reuse / ORM mismatch

**Problem:** The plan claims a `JSONText` TypeDecorator 'round-trips to the same TEXT the JS JSON.stringify writes.' Real divergences: (a) Python `json.dumps` defaults to `ensure_ascii=True` (escapes non-ASCII as \uXXXX) and inserts spaces after separators (`, ` and `: `), whereas JS `JSON.stringify` emits compact UTF-8 (`,`/`:`). Geopolitical content is heavy with non-ASCII names — so the same logical value serializes to DIFFERENT bytes. This isn't fatal for reads (both parse fine) but it (i) breaks any byte-equality contract/golden test the plan relies on as 'the literal definition of parity', and (ii) breaks `clue_snapshot`/delta diffing if any code compares serialized strings. The plan must use `json.dumps(x, ensure_ascii=False, separators=(',',':'))` to match. (b) Booleans: parties.ts stores `auto_discovered`/`user_verified`/`auto_generated` as INTEGER 0/1 and reads them back via `Boolean(row.x)`; SQLAlchemy with a Python `bool` column will write 0/1 too, but a naive Pydantic/Core mapping can emit Python `True`/`False` or `'true'` into a TEXT-ish path. Any mismatch (e.g., storing 'true' string) makes the TS `Boolean()` read truthy-but-wrong. (c) `forecast_resolutions.forecast`, `expert_councils.evidence_map`, `final_verdicts.scenarios_ranked` are TEXT-JSON the optimizer trainset and calibration depend on — a serialization drift there corrupts the eval loop's replayed inputs.

**Recommendation:** Specify the exact serializer (`ensure_ascii=False`, compact separators, stable key handling) in JSONText and add a round-trip test that writes a row in Python, reads it raw in the TS backend, and asserts logical equality (parse-and-compare, NOT byte-compare) — and separately a byte-compare test ONLY where the plan claims golden byte parity, downgrading that claim to semantic parity where bytes can't match. Map integer-booleans as `Integer` columns with explicit `int(bool)` coercion on write and `bool(int)` on read, mirroring parties.ts. Enumerate every TEXT-JSON column (22 tables) and assign each a typed codec; don't rely on one generic decorator.

### [MEDIUM] aiosqlite serializes writes through one worker thread, and the forum rewrites the whole session per turn; under the new fan-out the DB becomes a contention bottleneck the synchronous bun:sqlite baseline never had
**Area:** DB concurrency

**Problem:** TS uses bun:sqlite which is SYNCHRONOUS: every db.run blocks to completion, giving implicit serialization. The plan moves to aiosqlite (awaited, background thread per connection), holding the write lock across an await boundary. Two consequences under the redesign's concurrency: (1) Many concurrent STORM conversations writing clues/clue_versions + corpus rows now interleave and queue behind the writer / SQLite single-writer lock with busy_timeout waits. The forum is worse: writeForumSession (forum.ts) re-serializes and re-writes the ENTIRE session (all rounds+turns+scenarios via upsert) on EVERY turn, an O(turns) write that competes for the write lock. (2) research_searches has NO unique constraint (only research_pages has UNIQUE(topic_id,url)); two concurrent conversations that both miss findSimilarSearches and both storeSearch duplicate rows and double the live search. Async interleaving makes this check-then-act race far likelier than in the synchronous TS code.

**Recommendation:** Use a SINGLE writer connection behind a serialized write queue (one asyncio.Lock or a dedicated writer task), matching the TS's implicit serialization, with concurrent reads via WAL on separate read connections. Stop rewriting the whole forum session per turn: append the one new turn row (forum_turns has a stable PK + upsert) and only rewrite scenarios on scenario_interval. For the corpus race, add an in-process per-topic in-flight map of query->Future so concurrent identical searches/fetches await one live call (also collapses duplicate fetches). Confirm WAL checkpointing doesn't stall writers under the new write volume.

### [MEDIUM] DSPy synchronous forward() called on the shared event loop will freeze SSE delivery for ALL topics; the plan is internally inconsistent about sync vs async
**Area:** event-loop blocking

**Problem:** The plan contradicts itself: Foundations 6 and the Pipeline section wrap DSPy forward() in asyncio.to_thread 'because DSPy LM calls are sync', while Infra 2 and the STORM section assume fully-async aforward/acall. If any hot path calls synchronous dspy.Module.forward() (a blocking litellm completion) on the event loop, it blocks the loop for the entire multi-second-to-minutes call. Since the SSE bus, ping task, run tasks, and request handling all share one loop (the plan's stated in-process single-loop decision), one blocking LM call freezes ping delivery and event flushing for EVERY client across EVERY topic, producing frozen streams and reconnect storms. asyncio.to_thread mitigates per-call but the default pool is bounded (min(32, cpu+4)); the redesign's fan-out can exhaust it, re-serializing calls with the rate limiter now living in a different thread than the loop.

**Recommendation:** Commit to ONE concurrency model: use DSPy native async (aforward/acall + litellm acompletion) on all hot paths and forbid bare sync forward() in pipeline/agent code (lint/review rule). Where a sync primitive is unavoidable, route it through a single bounded executor sized deliberately and counted against the same global concurrency budget as the rate limiter, never the default unbounded to_thread pool. Add a watchdog test: run a long fake LM call and assert SSE pings keep flowing on a parallel connection. Resolve the doc inconsistency before Phase 1 so the STORM engine isn't built half-sync.

### [MEDIUM] Two backends on one SQLite file: non-pipeline writes (settings, prompts, providers, corpus, resolutions) are outside the advisory lock and collide during the migration window
**Area:** shared-DB concurrency

**Problem:** The pipeline_owner advisory lock only serializes PIPELINE runs per topic. Many writes are uncovered: app_settings (PUT /settings), prompt_configs (prompt edits AND the plan's optimizer writing instructions back), provider/custom-provider state, the corpus tables (written during research on EITHER backend), and forecast_resolutions. During migration both backends are live; an operator editing settings/prompts in the TS UI while Python runs a pipeline, or both backends writing corpus rows for the same topic, are concurrent writers. WAL allows one writer; bun:sqlite grabs-and-releases quickly, but aiosqlite holds the lock across an await, widening the SQLITE_BUSY window for the TS writer. busy_timeout=5000 turns this into multi-second stalls. The JSONText byte-compatibility is load-bearing and untested under interleaving: differing key ordering/whitespace/number formatting between Python and TS serializers could silently diverge a row updated by one and rewritten by the other.

**Recommendation:** Document and enforce that during migration, mutating non-pipeline endpoints (settings, prompts, providers) are served by exactly ONE backend, not both. Isolate ALL writes behind the single-writer queue so SQLITE_BUSY stalls never touch the event loop. Make the round-trip byte-compatibility test a Phase-0 gate and run it under interleaved write order, not just write-then-read. Forbid the DSPy optimizer from writing prompt_configs/.md while the TS backend may read them mid-run; gate optimizer writes behind cutover or a maintenance flag.

### [MEDIUM] Stacked retry layers (litellm + tenacity + adapter reparse + Refine/BestOfN + ensemble + ReAct loop + forum turns) amplify into unbounded LM-call cost with no global circuit breaker
**Area:** cost & failure amplification

**Problem:** Multiple retry/repeat layers compound multiplicatively with no shared ceiling: litellm num_retries, the LM-shim tenacity backoff, JSONAdapter reparse retries, Refine/BestOfN running the module N times, the scoring ensemble running N times, the ReAct agentic loop's maxIter rounds, and the forum's up-to-forum_max_turns sequential turns plus supervisor moderate/updateScenarios/compressHistory. A flaky proxy/provider (the exact case resolve_available_model exists for) under this stack turns one logical scoring into N_ensemble x N_refine x (1 + litellm_retries x tenacity_retries) provider calls against the rate-limited opus tier, cascading into 429s that trigger more retries. The TS baseline has only one retry layer (RETRY_BACKOFFS) plus ScenarioScorer's explicit 3x parse loop, far less amplification, and there is no per-run call/token circuit breaker.

**Recommendation:** Pick ONE retry layer and disable the rest (e.g., let the LM shim own retry/backoff, set litellm num_retries=0, and rely on typed OutputFields instead of adapter reparse loops where possible). Make Refine/BestOfN N and ensemble N explicit, small, and counted against the per-run budget. Add a global per-run circuit breaker (max LM calls / tokens / wall-clock) that aborts with a clean error event rather than grinding against 429s; this also protects against agent loops. Ensure a 429 that gets through backs off ONCE globally rather than per-layer, since the token bucket should make 429s rare.

### [MEDIUM] emit() is called synchronously from agent code that may run in a worker thread (to_thread) or DSPy callback context; put_nowait onto an asyncio.Queue from a non-loop thread is not safe
**Area:** bus thread-safety

**Problem:** The plan keeps emit() synchronous and non-blocking so agent code calls it 'like the TS emit with no await' (Cross-cutting 4). That is correct ONLY if emit() always runs on the event-loop thread. But the same plan runs DSPy forward() via asyncio.to_thread (Foundations 6, Pipeline) and uses a DSPy BaseCallback to emit think events on every LM/tool call. Those callbacks fire inside DSPy's execution context, which, if that execution is in a to_thread worker, means emit()->queue.put_nowait() runs from a non-loop thread onto an asyncio.Queue. asyncio.Queue is NOT thread-safe: put_nowait from another thread can corrupt internal state or, more subtly, fail to wake the awaiting get() in the loop (no call_soon_threadsafe), so events silently never deliver. This is intermittent and won't appear in single-threaded dev.

**Recommendation:** Decide the threading model first (see the event-loop-blocking finding). If any emit path can run off-loop, the bus MUST bridge via loop.call_soon_threadsafe(queue.put_nowait, event) (capture the loop at startup), or use a thread-safe queue (e.g. janus), or asyncio.run_coroutine_threadsafe. If you commit to fully-async DSPy with no to_thread, document and assert that emit() is loop-thread-only (check the running loop in debug builds). Add a test that emits from a worker thread and asserts the SSE consumer receives it, since this otherwise ships as 'sometimes the think feed just stops.'

### [MEDIUM] Polling request.is_disconnected() before a 15s blocking queue get risks zombie subscribers, and prod reverse-proxy SSE buffering can break the keep-alive
**Area:** SSE lifecycle

**Problem:** The stream generator loops on await request.is_disconnected() then await asyncio.wait_for(q.get(), timeout=15). request.is_disconnected() under uvicorn/Starlette is not reliable for a hard TCP drop (it depends on a disconnect ASGI message); a client that vanishes without a clean FIN can leave the generator parked in q.get() forever, holding a subscriber slot and a 1000-slot queue. With the frontend's auto-reconnect-every-3s-on-error, a flapping client accumulates orphaned subscribers that emit() still iterates and put_nowait's into. Checking disconnect only once per 15s extends the zombie lifetime. Separately, X-Accel-Buffering:no handles nginx, but the prod plan routes /api through a compose reverse-proxy/caddy whose SSE buffering defaults differ; if buffering is on, the 15s ping won't flush and the browser sees a dead connection and reconnect-storms.

**Recommendation:** Detect disconnect by writing, not polling: rely on the StreamingResponse raising on broken pipe when yielding and unsubscribe in the except; prefer sse-starlette (which implements ping + disconnect handling) over hand-rolling. Cap subscribers-per-topic and evict the oldest on overflow. Explicitly configure the chosen reverse proxy for SSE (proxy_buffering off / caddy flush_interval -1) and add a smoke test asserting a ping arrives within ~16s through the FULL proxy chain, not just against uvicorn. Make the ping double as a liveness probe whose write failure triggers immediate cleanup.

### [MEDIUM] Multi-turn forum debate is a stateful, externally-orchestrated loop that DSPy Signatures model awkwardly — and gain little
**Area:** DSPy fit for multi-turn forum debate

**Problem:** The plan models the forum as per-turn typed Predict calls (SpeakTurn, ModerateTurn, UpdateScenarios, CompressHistory) with a stateful ForumSupervisor dspy.Module wrapping three Predicts, and 'non-LLM bookkeeping ports as plain Python'. Reading ForumSupervisor.ts confirms the heavy lifting (turn_distribution, detectExchangeLoop, recentSpeakers window, budget warnings, compressed_history, persistence after every turn) is deterministic state mutation across up to 50 sequential turns — i.e. an external orchestration loop where each LLM call is a stateless single-shot. DSPy's value proposition (declarative signatures, optimizable demos, automatic parsing) is weakest exactly here: (a) the loop is inherently sequential and stateful, so dspy.Parallel/batch don't apply to turns; (b) there is no clean per-turn supervision label to optimize against, so the optimizer story doesn't reach the debate; (c) DSPy's stateful-module pattern (mutating self across forward calls) is explicitly discouraged and fights the framework's functional/compile model — DSPy modules are meant to be pure for compilation. Don't promise the chairman/turn-policy as an 'optimizable signature evaluated on coverage+calibration metrics' — there's no per-turn label and no data (Finding 1). The pragmatic win to claim is narrow and real: typed Literal outputs eliminate the JSON.parse-and-fallback in ForumSupervisor.moderate. Size DSPy's forum benefit accordingly so reviewers don't expect optimization magic in the debate.

### [MEDIUM] Adding DSPy + litellm in front of a working, OpenAI-compatible proxy injects a heavy, fast-moving dependency stack for marginal benefit on the agentic paths
**Area:** DSPy friction vs. current TS

**Problem:** Today the TS backend talks to CLIProxyAPI with a thin hand-written OpenAI-compatible client (proxyClient.ts) plus resolveAvailableModel. That keeps one dependency (or zero new ones) on the hot research path while still getting Signatures where they pay off. If DSPy is used broadly, pin litellm exactly, add a smoke test that exercises tool-calling + reasoning-model (model_type='responses') + streaming through the real proxy in CI, and budget for litellm/DSPy upgrade maintenance. Quantify in the plan what DSPy actually removes vs. what must be rebuilt around it, so the dependency cost is an explicit trade rather than an assumption.

### [MEDIUM] meta.create_all on a fresh dev DB produces a schema that diverges from the migrated live DB
**Area:** DB schema fidelity

**Problem:** The plan says Python's Table defs hold 'the final post-migration column set' and `create_all(checkfirst=True)` is 'a no-op against the existing DB' but also 'bootstraps a fresh dev DB.' These two goals conflict subtly. The live `dana.db` reached its schema through CREATE TABLE + a long series of idempotent `ALTER TABLE ADD COLUMN` migrations (fact_check, weight_evidence, moderator_directive/reason, parent_version, fork_stage, version_status, parties_snapshot, representatives_snapshot, completed_stages, evidence_map, debate_summary x2, steering) plus two post-hoc UNIQUE indexes. Column ORDER and the exact server_default strings differ between 'CREATE TABLE with everything inline' (what create_all does on fresh) and 'CREATE then ALTER ADD COLUMN' (what the live DB physically is). SQLite stores defaults and column order per the DDL path taken. A fresh Python-created DB will therefore NOT be physically identical to the live DB, so any test that assumes 'create_all reproduces the live schema' is testing a different schema than production, and a Python-bootstrapped dev DB could accept rows the live DB's stricter/looser defaults wouldn't.

**Recommendation:** Do not author Python Table defs by eye and hope they match. Reflect the LIVE schema (SQLAlchemy reflection / `inspect`) and snapshot it (`sqlite3 dana.db .schema`) as a golden artifact; assert the Python-bootstrapped schema's `.schema` matches the live one (normalizing whitespace). For fresh dev DBs, run the SAME ordered DDL+ALTER sequence the TS backend runs (or restore from a schema-only dump) rather than a single create_all, so dev == prod physically. Pin the two unique indexes explicitly.

### [MEDIUM] Forum turn-level resume is presented as a port but is actually NEW behavior — a parity risk, not parity
**Area:** Checkpoint resumability fidelity

### [MEDIUM] SSE emit() is synchronous in TS but crosses a task boundary in Python — drop-on-full and ordering can diverge
**Area:** SSE contract / async strategy

**Problem:** In TS, emit() is a synchronous fan-out (subscribers.get(id)?.forEach(cb)) executed inline within the pipeline call stack, so events are delivered in exact program order with no loss. The plan's Python bus uses `put_nowait` with `maxsize=1000` and 'drop on full', and pipeline tasks run as asyncio.create_task on the same loop. Two divergences: (1) DROPPING events on a slow/backpressured client is NEW behavior — TS never drops (it enqueues into a ReadableStream controller). For a long forum with hundreds of forum_turn/think events, a briefly-stalled EventSource could miss stage_complete or verdict_content, leaving the frontend stuck. The frontend's only recovery is the 3s reconnect on error, but a silent drop is not an error. (2) The DSPy work is largely SYNC (dspy.Predict/ChainOfThought); the plan elsewhere says run it in asyncio.to_thread. If emit() is called from a worker thread (to_thread) while the bus uses asyncio.Queue.put_nowait (not thread-safe across loops), you get a cross-thread queue mutation bug, not just an ordering nuance. The plan asserts 'because pipeline tasks run in the same event loop, put_nowait is safe' — but its own DSPy sections put the heavy work in threads.

**Recommendation:** Decide and document one model: either (a) keep ALL emit() calls on the event loop (don't emit from to_thread workers; marshal via loop.call_soon_threadsafe), or (b) use a thread-safe queue. Reproduce TS's no-drop semantics for terminal/critical events (stage_complete, verdict_content, error) — never drop those; only coalesce/drop high-volume think/progress. Add a backpressure test: a slow consumer must still receive the terminal events in order. Verify forum_turn ordering matches TS turn-for-turn.

### [LOW] Typed OutputFields reduce but do not eliminate parse fragility; the plan overstates 'no regex, no retry'
**Area:** DSPy maturity / structured output

**Problem:** The plan asserts the ~12 (actually 52, by grep, across agents) regex/JSON.parse sites 'collapse into typed OutputFields that the adapter parses, coerces, and validates' with 'no regex, no JSON.parse.' This is directionally true but optimistic in two ways. (1) DSPy's JSONAdapter relies on the underlying model honoring structured output / function-calling; proxied OAuth models behind CLIProxyAPI frequently do not, forcing ChatAdapter's *delimited text parsing* — which is itself a parser that fails on malformed output, just inside DSPy instead of in your code. (2) The plan keeps Refine/BestOfN 'for semantic validity' but also implies they replace the parse-retry — conflating two different retry needs. For deeply nested Pydantic (e.g. ScenarioEvidence with nested clue lists, or RankedScenario with dicts), weaker models behind the proxy will produce coercion failures the plan's own caveat acknowledges ('keep output models shallow').

**Recommendation:** Keep the claim but qualify it: typed Signatures remove *hand-written* regex from your codebase and centralize parsing/coercion in DSPy — a genuine maintainability win — but they do not remove parsing risk, especially through a proxy where native structured output is unreliable. Plan for the ChatAdapter text-parse fallback as the default (not the exception) for proxied models, keep output Pydantic models shallow (the score output already nests — flatten where possible), and keep a small validation+retry wrapper for the cases DSPy's adapter mis-coerces.
